**Title:** *Pour-El & Richards-style computable analysis: design feedback wanted
before scaling up*

---

Hi everyone — I'm starting a Lean 4 / Mathlib4 formalization of **computable
analysis in the style of Pour-El & Richards** (*Computability in Analysis and
Physics*, Cambridge UP 1989). The long-term target is upstream contribution
under `Mathlib.Computability.Analysis.*`. To my knowledge no formalization of
P-R-style computable analysis currently exists in Mathlib (or in any major
proof assistant — Coq's `CoRN`, Isabelle's `HOL-Analysis`, and the various
Lean experiments all use either Bishop-style constructive analysis or
TTE/represented spaces, neither of which is what P-R do). The current state
is: **L0 prerequisites stubs compile** at
[github.com/.../formal/ComputableAnalysis/L0/](https://github.com/...) — three
files (`Bridge.lean`, `PropB.lean`, `AnalysisBridge.lean`, ≈360 lines, 5
`sorry`s in theorem positions, all definitions concrete). The five sorries
are: `cantorPair_computable` (primitive-recursive composition), the four
clauses of Proposition B (recursively inseparable r.e. pair — recursion-theorem
fixed-point argument). Proposition B is not currently in Mathlib by any name
(verified via GitHub code search) and may itself be worth upstreaming once
proved.

The **architectural choice** that shapes the public API: a
`ComputabilityStructure` *typeclass* added to Mathlib's pre-existing
`[NormedAddCommGroup E] [NormedSpace 𝕜 E] [CompleteSpace E]`, with predicates
on sequences `ℕ → α` (a single element is computable iff its constant sequence
is). The substrate is Mathlib's `Computable` / `Partrec` — no oracle Turing
machines, no Type-2 TMs, no Baire-space realizers in the public API. We made
this choice over TTE / represented spaces (à la Pauly, Brattka, Schröder)
because P-R's framework adds structure to Mathlib's *existing* Banach-space
hierarchy without introducing a parallel category of "computable Banach
spaces" — which we judged would be the heavier upstream lift. We borrow
techniques from TTE/Weihrauch literature where they help, but state results in
P-R-shaped API. (We're aware this is a real design tradeoff and would value
pushback from anyone who has thought hard about TTE-in-Mathlib.)

One concrete naming question before we scale up — and this is the main reason
I'm posting here today. The L0 file introduces an **alias layer** mapping P-R
notation onto Mathlib names:

```lean
abbrev IsRecursive (f : α → β) : Prop := Computable f
abbrev IsRecursivelyEnumerable (A : Set α) : Prop := REPred (· ∈ A)
abbrev IsRecursiveSet (A : Set α) : Prop := ComputablePred (· ∈ A)
```

These exist purely to make P-R-citation comments and theorem statements read
the way P-R reads. **Are the L0 alias-layer names
(`IsRecursive`, `IsRecursivelyEnumerable`, `IsRecursiveSet`) ones you'd accept
upstream as part of `Mathlib.Computability.Analysis.Bridge`, or would you
prefer we drop the aliases and use `Computable`, `REPred`, `ComputablePred`
directly throughout?** Either is workable from our side; we'd like to make
this call once rather than churn aliases later. (Secondary question: if you
*do* want the aliases, would you prefer the project-internal name
`IsRecursivelyEnumerable` or shorter forms like `Mathlib`-house-style
`REPred`-aligned `IsREPred` / `IsRecursivelyEnumerablePred`?)

Repo (read-only, for context): \<repo URL\>. CLAUDE.md ≈ 210-line constitution
documents the four core architectural commitments. Happy to take feedback in
any form — DM, this thread, or a GitHub issue.

Thanks!
