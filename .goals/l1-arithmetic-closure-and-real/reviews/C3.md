## Hypothesis weakening
- Could the implicits be relaxed further (e.g., `[Computable r₁]`)? No —
  `IsComputableSeqRat` is the right hypothesis; relaxing it would change the
  theorem.
- Could the conclusion use `r₁ + r₂` (Pi-pointwise add) instead of
  `fun k => r₁ k + r₂ k`? **Yes, and probably should.** Mathlib's `Pi`-typeclass
  on `ℕ → ℚ` gives `(r₁ + r₂) k = r₁ k + r₂ k` definitionally, but callers in
  abstract settings (e.g., `Finset.sum`-based axiom_linearity downstream) will
  expect the `r₁ + r₂` form, and the current form forces a `show
  IsComputableSeqRat (r₁ + r₂) from ...`/`Pi.add_apply`-rewrite at call sites.
  Conventionally Mathlib uses the bare `+` form (compare `Continuous.add :
  Continuous f → Continuous g → Continuous (f + g)`, not
  `Continuous (fun x => f x + g x)`).
- Drop `private`? That's the whole point of the lift; can't drop the drop.

## Counterexample hunt
No counterexamples to the lemma itself (the proof was previously verified).
Fragile design points found:

1. **Name shape diverges from Mathlib convention.** Mathlib's pattern for
   predicate-closure is `<PredicateType>.<op>` with dot-notation, declared
   inside `namespace <PredicateType>`. Concrete confirmation:
   - `theorem Continuous.pow` at
     `.lake/packages/mathlib/Mathlib/Topology/Algebra/Monoid.lean:813`
   - `namespace Computable ... theorem const` at
     `.lake/packages/mathlib/Mathlib/Computability/Partrec.lean:263, 271`
     → callers write `Computable.const` / `h.pow`.
   The current shape `ComputableAnalysis.L1.isComputableSeqRat_add` is a
   snake_case sibling at the L1 module level, NOT inside a
   `namespace IsComputableSeqRat`. So callers write
   `isComputableSeqRat_add h₁ h₂`, not `h₁.add h₂`. This breaks dot-notation
   ergonomics for the imminent A1 proof. The blueprint label
   `lem:l1_isComputableSeqRat_add` likewise commits to the snake_case spelling.
2. **No `protected` modifier.** Once L1 is `open`-ed (as in CMap line 61), the
   theorem is visible by its tail name `isComputableSeqRat_add`. That's fine
   here but means there's no friction against unrelated downstream modules
   shadowing it. Compare Mathlib's `protected theorem Computable.partrec`.
3. **Conclusion uses η-form** `fun k => r₁ k + r₂ k` rather than `r₁ + r₂`.
   This will be a recurring papercut at every call site (the imminent A1
   axiom will iterate `_add` over `Finset.range (d n + 1)`, producing
   `Finset.sum`s whose internal shape will be `r₁ + r₂` Pi-style, not the
   η-form). Each call will need a `show ... from ...` adapter, or a follow-up
   `_add'` alias.

# Verdict reasoning
`concerns`, not `passes` and not `unsound`. The lift is technically correct
(builds clean, blueprint cite is accurate, the proof itself was previously
verified, no namespace collision). But the design has three ergonomic
weaknesses that a Mathlib-style maintainer would flag at PR review:
1. Snake-case name at module level, not dot-notation `IsComputableSeqRat.add`,
2. η-form conclusion instead of the `r₁ + r₂` Pi form,
3. Stale-by-design docstring metadata.

None of these are bugs in the *lift action itself* (the L4 file used the same
name and shape, so the lift is faithful). But the round was an opportunity
to fix all three before fanning out to `_mul`, `_reindex`, `_finsetSum` —
which will now perpetuate the same shape, and renaming later costs more.
